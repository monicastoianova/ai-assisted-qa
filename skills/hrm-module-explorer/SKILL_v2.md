# OrangeHRM Module Explorer

Autonomously explore an OrangeHRM module via Playwright, then write business-grade documentation to `docs/{module-slug}.md`.

## Step 1 — Parse Input

Extract the module name from the user message. If it is ambiguous or you cannot map it to a sidebar item, ask the user to clarify before proceeding.

## Step 2 — Login

1. `browser_navigate` → `https://opensource-demo.orangehrmlive.com/web/index.php/auth/login`
2. Fill **Username** `Admin`, **Password** `admin123`, click **Login**.
3. Confirm the dashboard loaded (snapshot). If login fails, report the error and stop.

## Step 3 — Navigate to Module

Click the matching item in the left sidebar. If not found, take a snapshot and ask the user which menu item corresponds to their request.

## Step 4 — Explore Every Submenu

0. First, open every dropdown/menu in the module's navigation and record the complete menu tree (including items that are direct links with no dropdown). This list is the coverage checklist for Step 5.

For each submenu item visible under the module:
1. Click it and call `browser_snapshot`.
2. Record: page title, section headings, visible tables/columns, form fields, buttons, and filter options.
3. Note any actions available (Add, Edit, Delete, Configure, Generate Report).

## Step 5 — Self-Reflection Checkpoint

After visiting all submenus, explicitly ask yourself:
- Re-open the module's navigation now and compare it against the menu tree recorded in Step 4. Do they match? Have I visited every item on it?
- Are there actions (e.g. modal forms, secondary tabs) I opened but did not document?
- Is each description based on **observed** UI, not inference?
- Does every behavioral claim satisfy Constraints rule 1? 

If any answer reveals a gap → go back and fill it.
If confidence on a feature is below ~80% → do **not** guess; add a `[needs clarification]` note and surface a question to the user in the **Open Questions** section.

## Step 6 — Write Documentation

Create `docs/{module-slug}.md` using the template below. `{module-slug}` is the lowercase, hyphenated module name (e.g. `leave`, `pim`, `recruitment`).

```markdown
# OrangeHRM — {Module Name} Module

> Auto-generated by the `hrm-module-explorer` skill on {DATE}

## Purpose
One paragraph — what business problem this module solves.

## Business Context
How HR teams use this module day-to-day and why it matters.

## Submodules / Features

### {Submenu Name}
**What it does:** …
**Who uses it:** …
**Key fields / actions:** …

## Relationships to Other Modules
- Bullet list of observed cross-module dependencies.

## Open Questions
- [ ] {question for low-confidence features, if any}
```

## Step 7 — Update CLAUDE.md

Append a row to the **Explored OrangeHRM Modules** table in `CLAUDE.md`:

```
| {Module Name} | [docs/{module-slug}.md](docs/{module-slug}.md) |
```

## Constraints

1. **Observed vs. assumed:** Document what IS on the page. Describe what an element DOES only if you performed the interaction in this session. Otherwise mark it "(assumed, not verified)" or move it to Open Questions.
2. **Structure, not data:** Record structure (menus, fields, buttons, labels), not data (record counts, record contents). The demo instance is shared and resets; data observations are valid only for the session.
3. **No destructive actions:** Never Save, Delete, Publish, or submit forms on the shared demo. Opening forms, dropdowns, and toggleable panels without saving is allowed.
4. **Describe elements as users see them** (e.g. "toggle/switch"), even if the accessibility tree reports a different role (e.g. "checkbox").
